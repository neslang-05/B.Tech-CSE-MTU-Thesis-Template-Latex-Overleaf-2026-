% AgriVerify --- AI-Powered Seed Quality Assessment and Farmer Feedback System

The backend of the AgriVerify system serves as the central coordinator for the entire platform. It handles the core business logic, coordinates the database schema, communicates with our specialized deep learning inference containers, and serves clean REST APIs for the Next.js frontend client. We developed this service using ASP.NET Core Web API on .NET 8, following the Clean Architecture pattern to keep the codebase modular, testable, and easy to maintain as requirements evolve.

By dividing the application into layers, we isolated our core domain entities and agricultural rules from external dependencies like database ORMs or third-party web frameworks. If we need to migrate from SQL Server to another database, or replace our external OCR API with a local model, we only need to write a new implementation in the infrastructure layer without changing our primary business services.

Adopting this layered design helps separate core business policies from technical details like web servers and database connections. This separation of concerns made it much easier to write automated unit tests for our verification services. We could mock the database interfaces and simulate seed verification workflows locally, even when working offline without access to our cloud database. Additionally, this structure allows us to scale individual layers independently; for example, the API controllers can be deployed to auto-scaling serverless containers while the database runs on a separate, dedicated resource.

\section{Domain Layer}
\label{sec:domain-layer}
% ============================================================

The Domain Layer contains the core business entities and contracts of the application. This layer is independent from external frameworks and infrastructure components.

\subsection{Core Entities}
Our domain layer defines the central models representing our business rules and database entities. The main entities include the base \texttt{User}, which is extended using ASP.NET Core Identity to support specific profile structures for \texttt{Farmer} and \texttt{Officer} accounts. The agricultural domain is modeled through \texttt{Seed} (defining reference cultivars) and \texttt{SeedBatch} (representing physical batches distributed by manufacturers). 

When a verification scan is processed, the system creates a \texttt{DetectionResult} containing model labels, confidence levels, and physical parameters. If a farmer reports an issue with a seed batch, a \texttt{Complaint} entity is generated to track the investigation details. Lastly, we log system actions through the \texttt{AuditLog} entity to maintain a clear record of administrative and verification changes.

\subsection{Interfaces}
To decouple our business logic from technical implementations, the domain layer defines generic and specific contracts. These include \texttt{IRepository} for abstracting database operations, and specialized service interfaces like \texttt{IVerificationService}, \texttt{IAuthenticationService}, \texttt{IComplaintService}, and \texttt{IAnalyticsService}. By coding against these interfaces rather than concrete classes, we can easily swap our storage engines or external AI service integrations during testing.

\section{Application Layer}
\label{sec:application-layer}
% ============================================================

The Application Layer coordinates business workflows and request processing.

\subsection{Application Services}
Our application services implement the core use cases of the platform. The \texttt{VerificationService} coordinates the image analysis workflow, handling validation, calling the ML inference API, and storing results. The \texttt{AuthenticationService} manages user accounts, password hashing, and token issuance. The \texttt{ComplaintService} handles farmer feedback submission and routing, while the \texttt{AnalyticsService} compiles performance trends. The \texttt{AdminService} provides tools for managing users and verifying system integrity.

\subsection{DTOs}

\section{Infrastructure Layer}
\label{sec:infrastructure-layer}
% ============================================================

The Infrastructure Layer manages database operations, external integrations, and cloud services.

\subsection{Database Management}
Database communications are managed through Entity Framework Core. The framework maps our C\char35{} classes directly to SQL Server tables, handles database transactions, and manages foreign key constraints. We use EF migrations to apply schema updates incrementally, keeping development and production databases synchronized.

\subsection{Repository Pattern}
We implemented the Repository Pattern to separate data querying from business logic. A generic repository provides common CRUD operations, while specialized repositories (such as the Seed and Complaint repositories) handle complex queries. This allows us to write optimized SQL joins when pulling verification histories and user profiles in a single query, avoiding the common N+1 query problem.

Complaints transition through multiple stages, with each action logged in a tracking table to maintain an audit trail. This prevents orphan records and ensures that all historical data remains traceable.

The security implementation focuses on protecting our API endpoints and data. When a user logs in, the backend issues an encrypted JWT token. The client includes this token in the header of subsequent requests. Our authentication middleware verifies the token signatures and checks the user's role before granting access. We also implement a refresh token rotation mechanism, allowing users to stay logged in securely without exposing long-lived access tokens. All passwords are hashed using BCrypt before database storage, and external communications require HTTPS connections.

The seed verification process is structured as a multi-stage workflow. When a farmer uploads an image, the frontend proxies the payload to our backend controllers. The request undergoes validation checks to verify file size and headers. An initial image quality step checks for severe blur or poor lighting, which could cause model misclassifications. If the image passes, it is uploaded to storage, and the backend triggers the ResNet50 model to analyze seed quality. Simultaneously, the OCR service extracts label data from the packaging. The backend saves the classification results to the database and uses Azure OpenAI to compile a plain-language summary for the user.

\section{Configuration and Deployment}
\label{sec:configuration-deployment}
% ============================================================

The backend uses multiple configuration files for different deployment environments. We store settings across \texttt{appsettings.json}, \texttt{appsettings.Development.json}, and \texttt{appsettings.Production.json}. These environment files keep sensitive information, like database connection strings, JWT signing keys, and cloud API credentials, separate from our application code.

During startup, \texttt{Program.cs} reads these configuration files to initialize our services. It configures the SQL Server DbContext, registers our domain services with the dependency injection container, enables the authentication and middleware pipelines, and configures logging via Serilog. This allows us to run the application with minimal dependencies during local development and easily switch to cloud databases and monitoring in our production environment.
