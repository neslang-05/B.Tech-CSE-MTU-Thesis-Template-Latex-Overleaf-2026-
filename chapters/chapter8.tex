This chapter details the system integration and communication framework of the AgriVerify platform. The architecture is designed to be highly modular, secure and extensible, decoupling the user interface (presentation tier) from the core business logic (application tier) and the specialized machine learning model serving components (inference tier) \cite{martin2018clean}. By separating these concerns, the system enhances maintainability, facilitates isolated component testing and allows each subsystem to scale horizontally based on computational demand.

\section{System Integration}

The AgriVerify architecture orchestrates communication across five distinct operational boundaries. To ensure data integrity, prevent unauthorized access and protect internal services, all client-to-server interactions are routed through a dedicated Next.js API proxy gateway \cite{nextjs2024}. This proxy layer acts as an intermediary, injecting security tokens and abstracting internal backend endpoints from direct exposure to the public internet, thereby mitigating potential cross-origin and data exposure risks \cite{masue2024quantifying}. \section{End-to-End Architectural Workflow}

Concurrently, a continuous integration and continuous deployment (CI/CD) pipeline automates system updates and resource provisioning. The detailed execution sequence for each operational phase is described below:

\begin{enumerate}
    \item \textbf{Client Submission and Proxy Routing (HTTPS):} The user initiates a verification request by uploading a high-resolution image of the seed packaging via the responsive web interface. This payload is transmitted over an encrypted HTTPS connection. The Next.js proxy gateway intercepts the request, appends the active JWT authentication token and coordinates silent token rotation if the token has expired, ensuring a seamless user session \cite{axios2024, jones2015jwt}.
    
    \item \textbf{Gateway Proxying and Backend Ingestion (REST API over HTTPS):} The proxy forwards the request payload to the internal ASP.NET Core API endpoints, effectively masking the internal network topology from the client. The backend server performs schema validation and prepares the image binary for downstream analytical processing \cite{freeman2020pro}.
    
    \item \textbf{Distributed AI Inference (HTTPS):} To optimize resource utilization and processing speed, the backend delegates analysis to specialized AI services rather than performing CPU-bound image processing locally. An initial quality check detects motion blur or inadequate illumination. Once cleared, the image is dispatched in parallel to three downstream models: Azure Cognitive Services for OCR text extraction (identifying batch numbers) and a custom ResNet50 convolutional neural network \cite{he2016deep, copard2020azure}.
    
    \item \textbf{Data Persistence (Azure Blob \& SQL Database):} Upon receipt of the model inference outputs, the backend commits the structured and unstructured data to cloud storage. The raw image is persisted in Azure Blob Storage, while the extracted metadata, quality assessment and transaction history are written to a secure Azure SQL Database, ensuring durability and traceability \cite{copard2020azure}.
    
    \item \textbf{Report Generation and Client Delivery:} The backend aggregates the analytical outputs and invokes Azure OpenAI to synthesize a cohesive, plain-language assessment report. The generated report is transmitted back through the API proxy to the client browser, rendering the results to the user within a low-latency window.
\end{enumerate}

In parallel, the \textbf{continuous deployment pipeline} operates asynchronously. Upon code commit to the version control system (GitHub), a CI/CD workflow builds container images using multi-stage Dockerfiles. These images are pushed to the Azure Container Registry (ACR) and subsequently deployed to Azure Container Apps (ACA), which dynamically scales resources horizontally based on real-time traffic demand \cite{merkel2014docker}.
