Deploying a trained model as a live service introduces a different set of problems than training it. Model development focuses on architecture and accuracy; the serving layer determines response latency, concurrent throughput, and uptime under real load \cite{martin2017clean}. In AgriVerify, the PyTorch ResNet-50 classifier from Chapter 4 runs inside a dedicated inference microservice built specifically for this purpose.

This chapter describes the design of that microservice, implemented with FastAPI and Uvicorn \cite{ramirez2023fastapi}. It covers the asynchronous request lifecycle, the tensor normalization pipeline, the API endpoint contracts, and the containerised deployment approach using Docker multi-stage builds on GCP Cloud Run \cite{merkel2014docker}.

\section{API Architecture and Request Orchestration}
\label{sec:api-architecture-overview}

\subsection{FastAPI and ASGI Serving Stack}
The inference microservice runs on FastAPI atop the Uvicorn ASGI runtime. FastAPI was chosen for its native async I/O support, Pydantic-based request validation and automatic OpenAPI schema generation \cite{ramirez2023fastapi}. Uvicorn's \texttt{uvloop}-backed event loop handles large numbers of concurrent connections with low memory overhead.

The stack separates network deserialization, Pydantic validation, OpenCV preprocessing and PyTorch execution into distinct layers. Computationally expensive inference operations run in dedicated thread pools and do not block the ASGI event loop.

\subsection{End-to-End Model Request Flow}
As illustrated in Figure~\ref{fig:model_request_flow}, an inference request begins when the ASP.NET Core backend sends a multipart POST containing a seed image. FastAPI validates the MIME type and payload boundaries, then decodes the byte stream into an OpenCV matrix in memory.

From there, two operations run in parallel: a PyTorch inference engine --- with ResNet-50 weights pre-loaded to avoid cold-start delays --- computes classification logits \cite{paszke2019pytorch, he2016deep}, while OpenCV contour routines extract 17 DUS (Distinctness, Uniformity, and Stability) morphological parameters \cite{bradski2000opencv}. The results are aggregated, scored against reference cultivars, and returned as JSON.

\section{Containerisation and Deployment Architecture}
\label{sec:containerization}

The service uses a multi-stage Docker build to balance reproducibility against image size \cite{merkel2014docker}. The \textbf{Builder Stage} compiles Python binaries (\texttt{.whl}) with \texttt{gcc}. The \textbf{Runtime Stage} copies those pre-compiled binaries into a minimal, security-hardened Debian base (\texttt{python:3.10-slim}), discarding the build toolchain entirely. The final image is approximately 850MB --- down from over 3GB --- with a correspondingly smaller attack surface.
