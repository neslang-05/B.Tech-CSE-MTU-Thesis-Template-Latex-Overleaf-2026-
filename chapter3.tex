\section{Overall System Architecture}
% ──────────────────────────────────────────────────────────────

The AgriVerify platform is engineered as a distributed, multi-tier web system
that integrates deep learning inference, cloud-based AI orchestration, and a
role-aware web application into a single coherent service. The system follows
the \textbf{Clean Architecture} (Onion Architecture variant), ensuring that the
core business logic remains completely independent of infrastructure concerns
such as databases, cloud vendors, or UI frameworks. Dependencies flow strictly
inward: the outer layers (Infrastructure, API) depend on abstractions exposed by
the inner layers (Application, Domain), never the reverse.

\medskip
At the highest level the system is composed of three major subsystems:

\begin{enumerate}
  \item \textbf{Deep Learning Microservice} — A PyTorch/ResNet-50 model trained
        on a 1{,}563-image paddy seed corpus and served as a containerised
        FastAPI endpoint on Google Cloud Platform (GCP).

  \item \textbf{Backend API} — An ASP.NET Core 8 Web API that acts as the
        primary orchestration layer. It authenticates users, mediates access to
        the ML microservice and Azure AI services (Custom Vision, AI Vision OCR,
        OpenAI), persists results to Microsoft SQL Server via Entity Framework
        Core, and exposes a versioned REST API consumed by the frontend.

  \item \textbf{Frontend Web Application} — A Next.js 14 App Router application
        with role-based dashboards for Farmers, Officers, and Administrators.
        All browser-to-backend traffic is forwarded through a server-side proxy
        route to avoid exposing credentials and to centralise authentication
        token injection.
\end{enumerate}

\medskip
The four architectural layers of the backend follow the Onion model:



\begin{enumerate}
  \item[Domain Layer] Contains core entities (\texttt{User},
        \texttt{VerificationHistory}, \\
        \texttt{ProductComplaint}), value objects,
        enumerations (\texttt{UserRole}, \texttt{VerificationStatus},
        \texttt{ComplaintStatus}), and domain exceptions. This layer carries no
        dependency on any framework or external service.

  \item[Application Layer] Orchestrates business workflows through application
        services (\texttt{VerificationService}, \texttt{UserService},
        \texttt{ComplaintService}), defines Data Transfer Objects (DTOs),
        AutoMapper profiles, and FluentValidation rules. It depends only on the
        Domain layer.

  \item[Infrastructure Layer] Provides concrete implementations for interfaces
        declared in the Application layer: EF Core repositories, the
        \texttt{ApplicationDbContext}, Azure service wrappers
        (\texttt{CustomVisionService}, \texttt{ComputerVisionService},
        \texttt{OpenAIService}, \texttt{BlobStorageService}), and migration
        management. This layer bridges the application to external systems
        without exposing implementation details upward.

  \item[API Layer] Hosts ASP.NET Core controllers
        (\texttt{AuthController}, \texttt{VerificationController},
        \texttt{ComplaintController}, \texttt{AdminController}), the JWT
        middleware pipeline, Swagger/OpenAPI documentation, and the global
        exception handling middleware.
\end{enumerate}

\section{Functional Requirements}
% ──────────────────────────────────────────────────────────────

The following functional requirements were derived from stakeholder analysis
and form the basis of the system implementation.

\subsection*{FR-01: User Registration and Authentication}
\begin{itemize}
  \item Farmers must be able to register using their name, email address, state,
        and district, and authenticate via email and password.
  \item Agricultural officers must authenticate using an officer ID and a
        time-based one-time password (OTP) as a second factor.
  \item Administrators are provisioned through database seeding with
        credentials managed by the platform.
  \item The system must issue JWT access tokens and refresh tokens upon
        successful login, and invalidate sessions on logout.
\end{itemize}

\subsection*{FR-02: Seed Verification}
\begin{itemize}
  \item Authenticated farmers must be able to upload front and back images of
        seed packaging for AI-powered authenticity analysis.
  \item The system must perform parallel inference using Azure Custom Vision
        for classification, Azure AI Vision for OCR text extraction, and Azure
        OpenAI for contextual report synthesis.
  \item A confidence score, verification status (Genuine / Counterfeit /
        Suspicious), extracted text, and a natural-language summary must be
        returned and persisted.
  \item An anonymous public verification endpoint must be available without
        requiring authentication.
\end{itemize}

\subsection*{FR-03: Complaint Management}
\begin{itemize}
  \item Authenticated farmers must be able to file complaints against seed
        batches, specifying issue type, district, severity, and
        optional image evidence.
  \item Officers must be able to view assigned complaints, update their status
        (Open / Investigation / Resolved / Closed), and record investigation
        actions with timestamps.
  \item Administrators must be able to view all complaints, filter by district
        and status, and assign unassigned complaints to officers.
\end{itemize}

\subsection*{FR-04: Role-Based Dashboards}
\begin{itemize}
  \item Farmers must have access to a personal dashboard showing verification
        history, complaint status, and summary metrics.
  \item Officers must be able to view a complaint queue, perform batch risk
        assessments, and access officer-level analytics.
  \item Administrators must have access to platform-wide analytics, user
        management, and reference data configuration.
\end{itemize}

\subsection*{FR-05: Batch Risk Registry}
\begin{itemize}
  \item The system must maintain a \texttt{BatchRiskRegistry} that aggregates
        complaint statistics per batch number, tracks affected districts,
        computes average severity scores, and assigns risk levels.
\end{itemize}

\subsection*{FR-06: Deep Learning Model Inference}
\begin{itemize}
  \item The ResNet-50 microservice must accept seed images, apply the
        224\,×\,224 preprocessing pipeline, run forward inference, and return
        class probabilities alongside 17 extracted DUS physical parameters
        (length, width, colour, texture, shape metrics).
  \item The microservice must perform variety matching against a reference
        database of 12 registered paddy varieties and return the top-3 matches
        with similarity percentages.
\end{itemize}

\section{Non-Functional Requirements}
% ──────────────────────────────────────────────────────────────

\begin{description}
  \item[NFR-01 — Performance]
        The end-to-end verification pipeline (image upload → AI orchestration →
        database write → response) must complete within a latency budget suitable
        for interactive web use. Parallel execution of the OCR and Custom Vision
        calls via \texttt{Task.WhenAll} is mandated to reduce blocking latency.
        The FastAPI microservice must serve single-image inference in sub-second
        wall-clock time on GCP Cloud Run hardware.

  \item[NFR-02 — Scalability]
        The backend must be stateless and deployable as a Dockerised container,
        allowing horizontal scaling without code changes. The frontend Next.js
        application must support server-side rendering and edge caching.

  \item[NFR-03 — Security]
        All HTTP traffic must be served over TLS (HTTPS). JWT access tokens must
        carry minimal claims and expire within a configurable TTL. Passwords must
        be stored as cryptographic hashes using PBKDF2 or bcrypt. Sensitive
        credentials (Azure keys, database connection strings, API keys) must be
        stored in environment variables and never hard-coded. Role-based endpoint
        protection must be enforced through ASP.NET Core \texttt{[Authorize]}
        policies.

  \item[NFR-04 — Reliability and Data Integrity]
        All grouped repository operations must execute within a Unit of Work
        transaction with atomic commit-or-rollback semantics. Soft-delete
        functionality must be implemented for complaint and verification records
        to support future legal auditing. Health check endpoints (\texttt{/health},
        \texttt{/api/health}) must expose the connectivity status of critical
        dependencies.

  \item[NFR-05 — Maintainability]
        The codebase must adhere to Clean Architecture layering with clear
        separation of concerns. Infrastructure services must be registered through
        an \texttt{InfrastructureServiceCollectionExtensions} extension class
        rather than inline in \texttt{Program.cs}. All public API endpoints must
        be documented via Swagger/OpenAPI 3.0.

  \item[NFR-06 — Usability and Accessibility]
        The frontend must deliver a responsive layout usable on both desktop
        browsers and mobile devices, supporting farmers who access the platform
        via smartphones. The UI must provide immediate loading feedback through
        skeleton placeholders and toast notifications for asynchronous operations.

  \item[NFR-07 — Portability]
        The deep learning microservice must be exported in multiple formats
        (\texttt{.pth}, TorchScript \texttt{.pt}, ONNX \texttt{.onnx}) to support
        deployment across different runtime environments. The entire application
        stack must be containerisable via Docker.
\end{description}

\section{Tools and Technologies}
% ──────────────────────────────────────────────────────────────

\subsection{Deep Learning Stack (PyTorch, ResNet-50)}

The classification model is implemented entirely in \textbf{Python 3.10} using
the following libraries:

\begin{itemize}
  \item \textbf{PyTorch} (\texttt{torch}, \texttt{torchvision}) — The primary
        deep learning framework used for model definition, training, and
        inference. PyTorch's dynamic computation graph simplifies debugging and
        enables flexible architecture modifications during the transfer-learning
        fine-tuning phases.

  \item \textbf{ResNet-50} — A 50-layer deep residual network pre-trained on
        ImageNet (1.2M images, 1{,}000 classes) sourced from
        \texttt{torchvision.models}. The backbone contributes approximately
        23.5M parameters; a custom three-layer classification head
        (2{,}048 → 512 → 128 → 3 units) adds a further 1.1M trainable parameters.

  \item \textbf{OpenCV} (\texttt{cv2}) — Used in the DUS parameter extraction
        pipeline for contour detection, pixel-to-millimetre calibration, and
        morphological analysis of seed images to compute the 17 physical
        parameters (colour mean/std, circularity, solidity, grain length/width,
        etc.).

  \item \textbf{NumPy / Pandas} — Numerical array manipulation and dataset
        statistics management.

  \item \textbf{scikit-learn} — Provides stratified train/validation/test split
        utilities and evaluation metric helpers.

  \item \textbf{Matplotlib / Seaborn} — Training curve visualisation and
        confusion matrix rendering.
\end{itemize}

\noindent
Training was conducted on a GPU-enabled environment with the \textbf{AdamW}
optimiser (weight decay $\lambda = 10^{-4}$), cross-entropy loss with label
smoothing ($\varepsilon = 0.1$), and a two-phase transfer learning schedule:
Phase 1 (Epochs 1--8, backbone frozen, LR $= 10^{-3}$) followed by Phase 2
(Epochs 9--15, full fine-tuning, LR $= 10^{-4}$).  The final ResNet-50 model
achieved a test accuracy of 99.57\% on the combined 1{,}563-image dataset with
a train-validation gap below 5\%.

\subsection{Model Serving (FastAPI, Docker)}

The trained PyTorch model is wrapped in a \textbf{FastAPI} microservice and
deployed as a Docker container on \textbf{Google Cloud Platform (GCP) Cloud
Run}. The inference pipeline within the microservice follows five stages:

\begin{enumerate}
  \item \textbf{Request} — The FastAPI endpoint receives a multipart image
        payload.
  \item \textbf{Preprocessing} — The image is resized to 224\,×\,224 pixels
        and normalised using ImageNet channel-wise mean
        $\mu = [0.485, 0.456, 0.406]$ and standard deviation
        $\sigma = [0.229, 0.224, 0.225]$.
  \item \textbf{Model Inference} — The ResNet-50 model processes the tensor
        and produces class logits.
  \item \textbf{Post-processing} — Softmax converts logits to probabilities;
        OpenCV routines extract the 17 DUS parameters; variety matching is
        performed against the 12-variety reference database.
  \item \textbf{Response} — A structured JSON payload containing the
        prediction label, confidence score, physical parameters, DUS
        classification, and top-3 variety matches is returned.
\end{enumerate}

\noindent
The model is exported in three formats to maximise deployment flexibility:
PyTorch native (\texttt{.pth}, ${\sim}$98\,MB), TorchScript (\texttt{.pt},
${\sim}$97\,MB for C++ runtimes), and ONNX (\texttt{.onnx}, ${\sim}$98\,MB
for cross-platform inference). Continuous delivery is automated via a
\textbf{GitHub Actions} CI/CD pipeline that triggers a Docker build-and-push
to GCP Artifact Registry on every push to the \texttt{main} branch.

% ──────────────────────────────────────
\subsection{Frontend Stack (Next.js, TypeScript, TanStack Query)}

The user-facing application is a \textbf{Next.js 14 App Router} single-page
application written in \textbf{TypeScript}. The key technology choices are
summarised below.

\begin{itemize}
  \item \textbf{Next.js 14 App Router} — Provides file-system-based routing
        with route groups that cleanly separate the three role namespaces
        (\texttt{(farmer)}, \texttt{(officer)}, \texttt{(admin)}). Server
        components are used for initial data fetching; client components handle
        interactive UI.

  \item \textbf{TypeScript} — Enforces strict compile-time type safety across
        all layers, including shared DTO interfaces (\texttt{src/types/}),
        domain service modules (\texttt{src/services/}), and custom hooks
        (\texttt{src/hooks/}).

  \item \textbf{TanStack Query (React Query v5)} — Manages all asynchronous
        server state: cache invalidation, background refetch, pagination, and
        optimistic mutation rollback. Query hooks are co-located with domain
        modules, with a global \texttt{QueryClient} that disables
        refetch-on-window-focus to reduce incidental network requests.

  \item \textbf{Zustand} — Lightweight client-side state store for
        authentication state (\texttt{user}, \texttt{token}, \texttt{role},
        \texttt{isAuthenticated}). The store is initialised from
        \texttt{localStorage} on the client side and exposes \texttt{setAuth}
        and \texttt{clearAuth} actions.

  \item \textbf{Axios} — Centralised HTTP client configured with a base URL
        of \texttt{/api/proxy}. A request interceptor automatically injects the
        Bearer token from storage; a response interceptor handles 401 errors
        by transparently attempting a token refresh before replaying the failed
        request.

  \item \textbf{Next.js API Route (Proxy)} — A server-side proxy route at
        \texttt{/api/proxy/[...path]} forwards browser requests to the
        ASP.NET backend at the URL stored in \texttt{BACKEND\_API\_URL},
        preventing credential exposure in the browser environment.

  \item \textbf{Tailwind CSS} — Utility-first styling with extended design
        tokens (colours, radii, shadows) defined in \texttt{tailwind.config.ts}.

  \item \textbf{Shadcn/UI + Custom Primitives} — A compact local component
        library providing Button, Input, Select, Dialog, Sheet, Table, Badge,
        Tabs, Skeleton, and Progress components implemented on native HTML with
        minimal abstraction overhead.
\end{itemize}

\noindent
Key design decisions reflected in the ER model include:

\begin{itemize}
  \item \textbf{Soft delete} via \texttt{IsDeleted} and \texttt{DeletedAt}
        fields on \texttt{VerificationHistory} and \texttt{ProductComplaint}
        to preserve audit trails.
  \item \textbf{3NF normalisation}: seed package information, verification
        records, and complaint data are stored in separate tables to eliminate
        redundancy.
  \item \textbf{Indexed columns}: \texttt{User.Email}, \texttt{VerificationHistory.UserId},
        \texttt{ProductComplaint.Status}, and
        \texttt{ProductComplaint.District} carry non-clustered indices to
        support dashboard query performance.
  \item \textbf{BatchRiskRegistry} is updated by a background aggregation job
        triggered on every complaint state change, acting as a denormalised
        risk summary table for fast officer-facing analytics.
\end{itemize}
