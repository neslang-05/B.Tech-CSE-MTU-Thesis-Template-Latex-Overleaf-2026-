\section{Architectural Overview}

The AI-Based Paddy Seed Quality Assessment And Farmer Feedback System employs a comprehensive backend architecture designed according to Clean Architecture principles, ensuring optimal separation of concerns and maintainability. This design paradigm facilitates loose coupling between core business logic and external dependencies such as databases, user interfaces, and third-party AI services. By adhering to these architectural principles, the system achieves high scalability, testability, and long-term maintainability essential for agricultural technology platforms.

\subsection{Architectural Layers}

The backend infrastructure is structured into four distinct, independent layers, each serving a specific purpose within the application ecosystem:

\subsubsection{Domain Layer}

The Domain Layer forms the foundation of the system, encapsulating core business entities, value objects, enums, and domain-specific exceptions. This layer remains completely independent from any external framework or infrastructure concern, representing the pure business logic of seed verification and quality assessment. It defines what the system does from a business perspective, free from technical implementation details.

\subsubsection{Application Layer}

The Application Layer orchestrates business logic by implementing application services and defining contracts through interfaces. It manages Data Transfer Objects (DTOs) for request-response mapping, establishes validation rules, and coordinates workflows between the Domain and Infrastructure layers. This layer depends exclusively on the Domain Layer, ensuring that business rules remain isolated and reusable.

\subsubsection{Infrastructure Layer}

The Infrastructure Layer implements concrete technical solutions including database access patterns using Entity Framework Core, integrations with Azure AI services (Custom Vision, Computer Vision OCR, and OpenAI), and cloud file storage mechanisms. It provides implementations for interfaces defined in higher layers while handling all external service integrations and data persistence operations.

\subsubsection{Presentation Layer (API Layer)}

The Presentation Layer serves as the application's entry point, handling HTTP requests, managing JWT-based authentication, and exposing RESTful API endpoints. This layer converts HTTP communication into application service calls and returns structured responses to clients while maintaining security through authorization and validation middleware.

\section{Project Structure Analysis}

\subsection{Domain Layer Architecture}

The Domain Layer encapsulates the fundamental business concepts of the Fake Seed Detection System. This layer contains core entities representing agricultural and administrative concepts, enums defining system states, interfaces specifying service contracts, and shared base classes providing common functionality.

\subsubsection{Entities Folder --- Core Business Models}

The Entities folder contains the primary business objects used throughout the system. Each entity represents a key concept in the seed verification and complaint management workflow:

\begin{description}
\item[BaseEntity.cs] Serves as the foundation for most domain entities, providing common audit properties including unique identifier, creation timestamp, modification timestamp, and audit trail information about entity lifecycle changes.

\item[Seed.cs] Represents the core seed entity containing agricultural product details necessary for verification operations.

\item[SeedBatch.cs] Models collections of seeds from a single production batch, enabling batch-level analysis and risk assessment across multiple products.

\item[DetectionResult.cs] Encapsulates the outcome of AI-based seed analysis, including confidence scores, classification results, and quality metrics.

\item[AnalysisReport.cs] Aggregates detection results and generates comprehensive reports suitable for farmer communication and administrative review.

\item[AuditLog.cs] Maintains detailed records of system operations and user actions for compliance, security auditing, and dispute resolution.
\end{description}

\subsubsection{Enums Folder --- System Classifications}

Enums maintain consistency by restricting values to predefined sets, preventing invalid state combinations:

\begin{description}
\item[SeedStatus.cs] Defines lifecycle states for seeds (Active, Suspended, Verified, Rejected).

\item[QualityLevel.cs] Classifies seeds into quality categories (Excellent, Good, Fair, Poor, Counterfeit) based on AI analysis.

\item[ImageFormat.cs] Enumerates supported image formats (JPG, JPEG, PNG) for seed packet analysis.

\item[DetectionAlgorithm.cs] Specifies available AI algorithms (Custom Vision, ResNet, Hybrid).

\item[ReportType.cs] Categorizes generated reports (VerificationSummary, DetailedAnalysis, RiskAssessment).
\end{description}

\subsubsection{Interfaces Folder --- Service Contracts}

Interfaces define contracts that promote testability and loose coupling throughout the system:

\begin{description}
\item[IRepository\textless T\textgreater] Generic repository interface providing standard CRUD (Create, Read, Update, Delete) operations while abstracting data access complexity from business logic.

\item[ISeedRepository] Extends the generic repository with seed-specific query operations optimized for verification workflows.

\item[IBatchRepository] Specializes repository operations for batch-level queries including batch risk assessment and historical analysis.

\item[IDetectionService] Defines contracts for image analysis and seed classification operations utilizing AI services.

\item[IReportService] Specifies interfaces for generating structured reports in various formats (PDF, Excel, JSON).

\item[IUnitOfWork] Implements the Unit of Work pattern for coordinating multiple repository operations within atomic transactions.

\item[IAuthenticationService] Defines security-related operations including user verification and access control.
\end{description}

\subsubsection{Common Folder --- Shared Base Classes}

The Common folder provides reusable base classes reducing code duplication:

\begin{description}
\item[BaseEntity.cs] Base class providing common audit fields (Id, CreatedAt, UpdatedAt, CreatedBy, UpdatedBy).

\item[Result\textless T\textgreater] Generic result wrapper enabling consistent error handling and operation status communication throughout the application.

\item[PagedResult\textless T\textgreater] Wrapper class supporting pagination in list operations, reducing database load for large result sets.

\item[ApiResponse] Standardizes HTTP response structure across all API endpoints.

\item[Pagination] Data transfer object containing pagination metadata (PageNumber, PageSize, TotalRecords).
\end{description}

\subsubsection{Exceptions Folder --- Error Handling Strategy}

Custom exceptions provide semantic meaning to error conditions:

\begin{description}
\item[DomainException] Base class for all domain-level business rule violations.

\item[EntityNotFoundException] Raised when requested entities do not exist in the system.

\item[ValidationException] Aggregates multiple validation failures with field-level details.

\item[UnauthorizedAccessException] Indicates insufficient permissions for requested operations.

\item[InvalidOperationException] Represents invalid state transitions or business logic violations.
\end{description}

\subsection{Infrastructure Layer Architecture}

The Infrastructure Layer implements technical solutions and external service integrations. It translates domain interfaces into concrete implementations while managing data persistence and cloud service communications.

\subsubsection{Persistence Folder --- Data Management}

The Persistence folder encapsulates all database-related operations:

\paragraph{ApplicationDbContext.cs}

The ApplicationDbContext class serves as the central Entity Framework Core context, mapping C\# domain entities to database tables. It manages:

\begin{itemize}
\item Entity-to-table mappings through DbSet properties
\item Database change tracking and automatic timestamp management
\item Soft delete functionality preserving historical records
\item Relationship configurations and constraints
\item Audit field population (CreatedAt, UpdatedAt automatically)
\end{itemize}

\paragraph{UnitOfWork.cs}

Implements the Unit of Work pattern coordinating multiple database operations as atomic transactions. When processing seed complaints with simultaneous investigation record creation, UnitOfWork ensures both operations commit together or both rollback, preventing data inconsistency.

\paragraph{Repository Implementation}

\begin{description}
\item[Repository\textless T\textgreater.cs] Generic repository implementing standard CRUD operations and reducing code duplication across entity-specific repositories.

\item[SeedRepository.cs] Provides seed-specific queries including batch-level searches and quality assessment lookups.

\item[BatchRepository.cs] Manages batch operations including risk analysis and historical trend queries.

\item[DetectionResultRepository.cs] Specializes in verification result retrieval and analysis queries.
\end{description}

\subsubsection{Configurations Folder --- Database Mapping}

Entity Framework Core configuration classes define database schema, indexes, and relationships:

\begin{description}
\item[SeedEntityTypeConfiguration] Defines table schema, column types, constraints, and indexes for optimal seed query performance.

\item[BatchEntityTypeConfiguration] Configures batch table structure with relationships to seed and result entities.

\item[ResultEntityTypeConfiguration] Maps detection result schema with confidence score storage and enum conversions.

\item[AuditLogConfiguration] Establishes audit log structure with timestamp indexing for efficient historical queries.
\end{description}

\subsubsection{Migrations Folder --- Schema Version Control}

Database migrations enable safe schema evolution without data loss:

\begin{itemize}
\item Initial migrations create core tables and relationships
\item Incremental migrations add features (new columns, tables, indexes) as application requirements evolve
\item Migration history enables rollback to previous schema versions if necessary
\item Each migration is timestamped and sequenced for deterministic application
\end{itemize}

Example migrations include:

\begin{description}
\item[20240101000000\_InitialCreate.cs] Creates foundational entities (Seed, Batch, User, DetectionResult).

\item[20240115000000\_AddDetectionTables.cs] Introduces AI analysis and verification result tables.

\item[20240201000000\_AddAuditLog.cs] Adds comprehensive audit logging capability.
\end{description}

\subsubsection{Services Folder --- External Integrations}

External service integration classes manage cloud and AI service communications:

\begin{description}
\item[CustomVisionService.cs] Interfaces with Azure Custom Vision API for seed image classification, returning confidence scores and classification results.

\item[ComputerVisionService.cs] Validates image quality (brightness, sharpness, resolution) before expensive cloud processing, reducing costs and protecting privacy.

\item[OpenAIService.cs] Utilizes GPT models to generate farmer-friendly explanations from technical verification results.

\item[BlobStorageService.cs] Manages Azure Blob Storage operations for secure image uploads and retrievals without local server storage.

\item[ResNetPaddyClassifierService.cs] Provides custom-trained deep learning model specifically for rice seed classification, offering superior accuracy compared to general-purpose models.
\end{description}

\subsubsection{Extensions Folder --- Dependency Injection}

The InfrastructureServiceCollectionExtensions class centralizes service registration:

\begin{itemize}
\item Registers database contexts and Entity Framework Core configuration
\item Configures repository instances and Unit of Work pattern
\item Registers external service implementations (AI, storage, authentication)
\item Organizes dependency injection into logical, reusable extension methods
\item Maintains clean Program.cs by centralizing infrastructure setup
\end{itemize}

\item[AdminDashboardResponse] Aggregates system overview statistics including user counts and complaint metrics.

\section{Data Flow and Integration Points}

\subsection{Verification Workflow}

The seed verification workflow demonstrates the integration of architectural layers:

\begin{enumerate}
\item \textbf{API Request:} Farmer uploads seed packet images through VerificationController.
\item \textbf{Request Validation:} VerificationRequestValidator ensures image format and size compliance.
\item \textbf{Service Orchestration:} VerificationService coordinates multiple processing steps.
\item \textbf{Image Quality Analysis:} ComputerVisionService evaluates image quality locally.
\item \textbf{AI Classification:} CustomVisionService classifies seed authenticity via Azure API.
\item \textbf{Text Extraction:} Computer Vision OCR extracts batch numbers and brand information.
\item \textbf{Result Explanation:} OpenAIService generates farmer-friendly summaries.
\item \textbf{Data Persistence:} Repository pattern saves verification results to database.
\item \textbf{Response Mapping:} AutoMapper transforms domain entities to VerificationResponse DTO.
\item \textbf{API Response:} Controller returns structured response to farmer with verification results.
\end{enumerate}

\subsection{Security Architecture}

The system implements multiple security layers:

\begin{description}
\item[Authentication] JWT Bearer tokens issued upon login, validated in every protected request.
\item[Authorization] Role-based access control (Farmer, Officer, Admin) enforced per endpoint.
\item[Password Security] ASP.NET Core Identity manages hashing and complexity validation.
\item[Session Management] Refresh tokens enable persistent sessions with expiration enforcement.
\item[API Security] Middleware validates tokens, prevents unauthorized access.
\item[Data Encryption] Sensitive data encrypted in transit (HTTPS) and at rest (database).
\end{description}
